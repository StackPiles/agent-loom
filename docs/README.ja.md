# Agent Loom

**ローカルLLMと、仕事を進めて相談し合うボットたちのためのワークスペース。**

[English](../README.md) · [詳しいインストール方法](INSTALL.md) · [モデル・並列実行の設定](MODELS.md) · [設計](ARCHITECTURE.md) · [参考プロジェクトの調査](RESEARCH.md)

Agent Loom は、複数ボットとの会話、作業の進捗、具体的な操作の承認、定期実行、記憶とスキルの管理を一つにまとめたセルフホスト型アプリです。用意した OpenAI 互換の推論サーバーに接続して使います。

ブラウザー画面とアプリのバックエンドは手元のマシンで動作します。推論サーバーの場所は自由に選べます。モデル本体や有料モデル契約は付属しません。TypeScript、React、Node.js、SQLite、Pi SDK を使った、独立したオープンソースプロジェクトの **v0.3.0** です。

## できること

| 機能                 | 動作                                                                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 永続的なグループ会話 | 部屋、参加ボット、会話を保存します。画面を移動しても、アプリを再起動しても見返せます。                                                         |
| 短いメンション       | 内部IDではなく `@aster`、`@nova` のような短いハンドルで指定します。                                                                            |
| ボット同士の連携     | ボットごとに役割と指示を持たせ、別のボットに作業を依頼できます。往復回数には上限があります。                                                   |
| 作業の見える化       | 待機中、推論中、ツール実行中、承認待ち、停止、中断、失敗を区別します。停止・明示的な再開に対応します。                                         |
| 具体的な承認         | 対象と実際の引数を確認して承認・拒否します。「自動判定」では限定した低リスク操作を自動承認し、理由を表示します。                               |
| 思考の表示           | 対応モデルが返した思考を回答と分けて表示します。思考を返さないモデルについて、内容を補完して作ることはありません。                             |
| 画像生成             | 会話用とは別の画像生成モデルを設定し、ボットが呼び出せます。生成画像はチャットに保存され、表示・ダウンロードできます。                         |
| 並列推論             | 同時リクエスト数を1～16に設定できます。ルーム内の並列応答は個別に選べ、同じボットとルームのセッションは重複して動かしません。                  |
| プロアクティブな処理 | 定期実行、URLの変化、Webhook、接続したアカウントの新着メールをきっかけに、指定した部屋とボットへ作業を渡します。                               |
| ボットのメール       | IMAP/SMTP、AgentMail、Resend Inboxesの既存アカウントを接続します。ボットへの割り当て、検索・本文の閲覧、下書き、内容確認後の送信に対応します。 |
| サービス台帳         | ボットごとにサービスのURL、ログイン名、登録メール、利用状態を管理します。任意の秘密情報はバックエンドで暗号化して保存します。                  |
| アプリ内通知         | 作業に関連した通知を受信箱に残し、元の会話へ移動できます。                                                                                     |
| 記憶とスキル         | 継続して使うメモと再利用する手順を分けて管理します。スキル候補の確認、有効化、版の復元、Markdown出力ができます。                               |
| Webツール            | URLの読み取りと、SearXNGまたはBrave Searchを使った検索に対応します。この検索機能にMCP接続は不要です。                                          |
| 推論設定             | 接続先、モデルID、コンテキスト長、出力上限、温度、任意の思考設定を指定します。トークン数は2の累乗から選び、既存の端数の値も保持します。        |

ここでいう「成長」は、経験を記憶や再利用する指示として残すことです。モデルの重みを学習し直す機能ではありません。自動生成されたスキル候補は内容を確認してから有効にできます。蓄積が増えれば必ず性能が上がる、という保証もしません。調査した証拠と採用した設計は [RESEARCH.md](RESEARCH.md) にまとめています。

## 作業状況と承認待ち

入力欄のすぐ上に **「ボットの状態」** を表示します。会話をスクロールしていても、各ボットの「順番待ち」「生成枠待ち」「生成準備中」「思考を生成中」「回答を生成中」「ツール実行中」「承認待ち」「停止済み」「中断」「エラー」「完了」を確認できます。対象のボットを停止・再開したり、状態を選んで該当する実行内容へ移動できます。

承認が必要になると、同じ場所に **承認待ちの件数とボット名** を表示します。別のボットが生成中でも、元の承認カードが古いメッセージにあっても確認できます。**「確認する」** で承認待ちの一覧を開き、対象と実際の引数を確認して、操作ごとに許可・拒否してください。外側のクリック・Esc・閉じるボタンは一覧を閉じるだけで、承認内容は変更しません。会話内のカードにも同じ内容が残り、一方で送信中の判断をもう一方から重複送信することはできません。

サイドバーのルームとブラウザーのタブにも承認待ちの件数を表示します。別ルームに承認待ちがある場合は、該当するルーム・ボットへの案内を表示します。承認の到着で会話のスクロール位置を勝手に動かしません。

停止・完了後や過去の実行では、古い生成カーソルや処理中アニメーションを残しません。接続が切れた場合は **「状態を確認できません」** と表示します。これは画面が最新の状態を取得できないことを意味し、サーバー上の作業が停止したと断定する表示ではありません。

## メールとサービスアカウント

**「メール・サービス」→「メール」→「メールを接続」** から、既存のメールボックスを接続できます。メール基盤はLoomの外で管理します。Loom自体がメールサーバーを動かしたり、ドメインや外部メールボックスを作成したり、提供元の契約・課金を管理したりする構成ではありません。メール基盤を決めてから接続しても、ルーム・ボット・自動化の使い方は共通です。

| 接続方式       | 設定する内容                                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IMAP / SMTP    | メールアドレス、受信サーバー・ポート、TLSまたは必須STARTTLS、ユーザー名・パスワード。送信する場合はSMTPも設定します。対応するホスティングサービスや自営サーバーに接続できます。 |
| AgentMail      | 作成済みの受信箱ID、そのメールアドレス、受信箱にアクセスできるAPIキー。                                                                                                         |
| Resend Inboxes | 作成済みの **Inbox** のID、そのメールアドレス、必要な権限を持つAPIキー。送信専用のResendドメインだけでは受信箱になりません。                                                    |

接続ごとに利用するボットを選びます。割り当てはルームから独立しているため、そのボットは参加している別のルームでも同じメールを利用できます。送信権限の初期値は **「送信内容を確認して承認」** です。アカウント単位で、割り当てたボットの送信を許可したり、送信を禁止したりできます。ネットワーク権限も適用されます。

**「接続をテスト」** は、フォームの設定を使って接続を確認します。設定は保存せず、メールも送信しません。IMAPでは読み取り専用の受信箱接続と、設定済みならSMTP認証を確認します。API方式では指定した受信箱へのアクセスを確認します。テスト成功は、宛先への配達や、提供元側のすべての送信権限を保証するものではありません。パスワード・APIキーは設定欄に入力し、バックエンドで暗号化して保存します。保存済みの値はアカウント情報やボットのツール結果に返しません。接続先・アカウント・受信箱を変更すると、該当する入力済み認証情報を消去します。

接続を選ぶとメールの一覧・検索・本文を確認できます。本文はテキストとして表示し、メールのHTMLや外部画像を読み込みません。添付ファイルは情報の一覧のみで、アップロード・ダウンロード、アーカイブ、削除、既読化は未実装です。**「メールを作成」** と **「返信」** は、まずLoom内の下書きを保存し、差出人・To/Cc/Bcc・件名・本文を確認してから送信します。ボットも同じ下書きと送信処理を使い、初期設定では承認カードに送信内容全体を表示します。承認待ちの間に下書きやアカウント設定が変わった場合、古い承認では送信しません。

**「送信履歴」** は、Loomから行った送信の記録です。「送信済み」は提供元が送信を受け付けた状態を示し、相手への配達・開封を確認した意味ではありません。結果が不明な場合は **「状態を確認」** を表示し、自動では再送しません。別のメールを作成する前に、提供元の送信履歴を確認してください。ダイアログを閉じたりブラウザーの接続が切れたりしても、すでに受け付けられた送信が取り消されたとは限りません。

**「自動化」→「新着メール」** では、担当ボットに割り当てた接続を選び、ルーム・間隔・処理内容を指定します。例えば「新しい請求書の本文を確認し、対応が必要なものを通知して」と依頼できます。新着イベントのメールIDから、ボットが必要な本文を読み取れます。前の処理でボットが動いている間も受信チェックを続け、未処理の新着を順番に渡します。メール接続の停止・解除や、そのボットの割り当て解除では、該当する自動化を停止します。Loom上で接続を解除しても、外部メールボックスは残ります。

**「メール・サービス」→「サービス」** には、サービス名・URL・ログイン名・利用するボット・登録メール・利用状態・メモを保存します。ボットのサービスに関連付けるメールも、そのボットに割り当て済みである必要があります。必要なら専用欄にパスワードやAPIキーを保存できますが、保存後の値は画面やモデルに返しません。ボットは自分に割り当てたサービス情報を確認し、承認を求めて台帳を更新できます。外部サービスへの自動登録、自動ログイン、保存した秘密情報のChromeへの自動入力、ボット別ブラウザープロファイルの作成は、この台帳には含まれません。既存のChrome操作とその権限は別の機能です。

既存のIMAP監視でログイン名がメールアドレスになっている設定は、起動時に共通の受信用接続へ移行します。SMTPは自動で追加しません。送信元アドレスを安全に決められない従来設定は、従来のIMAP経路を維持します。実サービスでの動作は提供元のAPI・アカウント・権限に依存し、自動テストは制御したフィクスチャーで確認しています。

## Chromeの操作

**「設定」→「Chrome操作」** で有効にし、接続方法を選んで **「保存して接続」** を押します。Chrome DevTools公式のMCPを同梱しているため、Pythonの導入やMCP設定ファイルの作成は不要です。

- **普段のChrome**：Chrome 144以降で `chrome://inspect/#remote-debugging` を開き、リモートデバッグを有効にします。Loomから接続したら、Chrome側の接続確認を許可してください。
- **専用のChrome**：インストール済みのChromeを、Loom専用のプロファイルで開きます。必要なサイトへのログインはこのウィンドウで行います。

ボットはタブの一覧・新規表示、ページの読み取り、クリック、入力、キー操作、スクロール、スクリーンショットに対応します。テキスト専用のローカルLLMでも、ページのアクセシビリティ情報を読んで操作できます。スクリーンショットはチャットに表示されます。画像をLLMにも渡す場合だけ、画像入力対応モデルを使い **「スクリーンショットをモデルにも送る」** を有効にしてください。

Chrome用の権限は独立しています。「自動判定」ではタブ一覧・ページ読み取り・スクリーンショットを自動承認し、クリックや入力などは対象と内容を表示して確認します。推論が並列でも、Chrome操作はボット全体で順番に実行します。「切断」後は、明示的に接続し直すまでボットが勝手に再接続しません。

操作するのは **Loomのサーバーが動いているPCのChrome** です。例えばWindowsでLoomとChromeを動かし、推論だけ別のGPUマシンへ接続できます。ブラウザー画面だけをWindowsで開いても、遠隔サーバーからWindowsのChromeを操作することはできません。標準Docker構成にはChromeやデスクトップは含まれません。詳細は [Chromeの接続・操作ガイド](BROWSER.md) を参照してください。

## システムプロンプトの生成支援

**「ボット」→「編集」または「ボットを追加」→「生成支援」** を開きます。「どんな仕事を任せたいですか？」に担当業務や話し方を入力してください。入力済みの役割が初期値になります。既存のプロンプトがある場合は「現在のプロンプトを基に改善する」を選べます。オフにすると新しい案を作ります。

「案を生成」で、設定済みのLLMが案を生成します。順番待ち・生成中の状態と途中の文章を表示し、完了後はその場で編集できます。「この案を取り込む」は編集欄への反映だけで、「元に戻す」で取り込み前の文章に戻せます。最後に「保存する」でボットに適用してください。

生成はチャットと同じ推論枠を使用し、停止もできます。画面を閉じても生成は続き、「生成支援」を再び開くと最近の結果を確認できます。デモモードでは生成できないため、実際のLLMを設定してデモをオフにしてください。制限の詳細は [モデル設定](MODELS.md#system-prompt-assistance) に記載しています。

編集ダイアログ、ルームの操作メニュー、メンション候補は外側のクリックで閉じます。プロフィールの未保存の編集内容は破棄されますが、サーバーに生成された案は履歴に残ります。ダイアログ内の操作や、内側から外側への文字選択ドラッグでは閉じません。Esc は手前のポップアップから閉じます。

## 最短で起動する

**Node.js 24 LTS** と **Git** をインストールし、ターミナルで実行します。

```sh
git clone https://github.com/StackPiles/agent-loom.git
cd agent-loom
npm ci
npm run build
npm start
```

**http://127.0.0.1:3210** を開いてください。Windows、macOS、Linuxで同じコマンドを使います。WindowsのPowerShellで `npm.ps1` の実行が止められる場合は、`npm` の代わりに `npm.cmd` を使えます。

**設定**を開き、推論サーバーのベースURL、モデルID、必要ならAPIキーを入力します。画面上部の **EN / 日本語** で表示言語も切り替えられます。

| 推論サーバーの例       | 同じPCで動かす場合のベースURL例         |
| ---------------------- | --------------------------------------- |
| LM Studio              | `http://127.0.0.1:1234/v1`              |
| Ollama                 | `http://127.0.0.1:11434/v1`             |
| llama.cpp のポート8080 | `http://127.0.0.1:8080/v1`              |
| LAN内の別PC            | `http://サーバーのIPアドレス:ポート/v1` |

ポート番号は推論サーバー側の設定に合わせてください。モデルIDには、サーバーが実際に提供している識別子を使います。

ツール操作やボット間の依頼には、モデルと推論サーバーの **OpenAI互換ストリーミングチャット・ツール呼び出し対応**が必要です。接続確認でモデル一覧が取得できても、ツール呼び出しまで正常とは限りません。まず短い会話を試し、次に「AsterからNovaに別の観点を聞いて」などの小さな依頼を送り、作業履歴を確認してください。

**推論の詳細設定**では、コンテキストと出力のトークン数を `2^15 · 32,768` のような候補から選べます。コンテキストは最大 `2^21`（2,097,152）、出力は最大 **1M = `2^20`（1,048,576）**で、保存済みの端数の値もカスタム値として保持します。出力上限はコンテキストより小さくする必要があるため、小さいコンテキストを選べない場合は先に出力上限を下げてください。コンテキストは入力・履歴・出力の合計なので、**1Mコンテキストでは出力512Kまで、2Mコンテキストでは出力1Mまで**を2の累乗で選べます。保存済みの設定や初期値は自動では増やしません。Loom側の数値を増やしても、推論サーバーの実際の対応範囲は変わりません。

思考設定は通常 **サーバー既定** のまま使います。サーバーが `reasoning_effort` に対応している場合は **OpenAI互換** に切り替え、`none`・`minimal`・`low`・`medium`・`high`・`xhigh`・`max`・`ultra` から選べます。選んだ値をそのまま送信し、低い段階へ自動で置き換えません。`ultra` などの拡張値は共通規格ではなく、接続先の対応が必要です。表示には、モデルが思考テキストを返す必要があります。思考は回答と別に保存され、停止・中断や表示上限による省略も区別されます。

操作の権限には **毎回確認・自動判定・許可・拒否** があります。自動判定は固定ルールで、公開Webの読み取り、設定済みの検索サービス、限定した作業フォルダの確認、新しい文書（`.md`・`.txt`・`.csv`・`.tsv`、64 KiB以下）の作成を自動承認します。既存ファイルの上書きや任意のシェルコマンドは確認が必要です。自動承認の理由は作業履歴で確認できます。既存の権限設定は変更するまで維持されます。

自動承認したWeb取得でも、リダイレクト先を確認します。認証情報を含むなどの理由で自動承認できない転送先には接続せず、作業ログに理由を表示します。その取得を確認して進める場合は、ネットワーク権限を「毎回確認」に変更して再度依頼してください。

## キャラクターのアバター

**ボット → プロフィール**で、Aster・Nova・Orbit・Moss・Luna・Pip・Sage・Bramの8種類から選べます。標準画像はアプリに同梱しているため、画像モデルの設定は不要です。以前のAster/Novaの初期アイコンは一度だけキャラクターに更新し、自分で変更したアバターは保持します。

**アクセントカラー**を選ぶと、画像アバターを囲む枠の色が変わります。自分で生成した画像にも反映されます。プロフィールではキャラクターと色をすぐにプレビューでき、**保存**するとチャット・メンバー表示・ボットカードにも反映されます。

自分で作る場合は、**設定 → 画像生成**で画像モデルを設定してから、プロフィールでキャラクターの説明を入力して生成してください。待機・生成中の状態と取消を表示します。**結果をプレビュー → プロフィールに選択 → 保存**の順で反映します。閉じたり再起動したりしても、最近の生成結果から選び直せます。会話用LLMを動かさずに、設定済みの画像モデルを直接使います。

「生成」を押すことでその画像リクエストを実行します。ネットワーク権限が「拒否」の場合は生成できません。画像と会話の推論枠を共有する設定にも従い、停止・失敗・再起動後に勝手に再生成しません。標準画像と生成の詳細は [AVATARS.md](AVATARS.md) にまとめています。

## ルームごとの作業フォルダー

このバージョンは、一つのアプリ用データフォルダーにルーム、ボット、設定、会話を保存します。サイドバーにはそのアプリを表示し、複数のワークスペースを切り替える機能はありません。ルームの「作業場所」は、ファイル操作やコマンドを実行するフォルダーのことです。

ルームのメニュー → **ルームを編集** → **このルームの作業場所** から、**フォルダーを選択**を押してください。新しいルームの作成時にも設定できます。保存すると、そのルームのボットや自動処理が選んだ場所を使用します。**既定の場所に戻す**でルーム固有の設定を解除すると、「設定」の既定フォルダーを使います。

WindowsでNode版を同じPC上で動かし、`localhost` またはループバックIPから開いている場合は、Explorer形式のOS標準フォルダー選択ダイアログが開きます。フォルダーをアップロードする処理ではありません。選択やフォームをキャンセルした場合は元の設定を保持します。

macOSでは標準のフォルダー選択、Linuxデスクトップでは利用可能な `zenity` / `kdialog` を使います。Docker・画面のないサーバー・別PCやプロキシ経由の接続では、このデスクトップ選択は使えません。その場合は明示的な手入力欄から、サーバー上のパスを指定してください。Dockerではホストの場所をマウントしたうえで、コンテナ内のパスを使います。

作業中のルームでは、先に作業を停止してからフォルダーを変更してください。各作業は開始時の保存先を記録します。変更後の場所で進める場合は新しく依頼し、古い作業を再開する場合は元のフォルダーに戻します。

## Dockerで使う

リポジトリを取得し、`.env.example` を `.env` にコピーします。`LOOM_API_TOKEN` に長いランダムな値を設定してください。これはアプリを開くためのトークンで、推論サーバーのAPIキーとは別です。

Nodeが入っている場合、次のコマンドで値を生成できます。DockerホストにNodeを入れない場合は、パスワードマネージャーなどで生成しても構いません。

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

設定後、起動します。

```sh
docker compose up --build -d
docker compose logs -f loom
```

**http://127.0.0.1:3210** を開き、設定したトークンを入力します。データは `loom-data` ボリュームに保存されます。付属のCompose設定は、ホストのループバックアドレスだけにポートを公開します。

推論サーバーがDockerホスト側にある場合、Loomの接続先は `http://host.docker.internal:1234/v1` のように指定してください。コンテナ内の `127.0.0.1` はコンテナ自身を指します。推論サーバー側でも、Dockerから接続できる待ち受けアドレスとファイアウォール設定が必要です。

`docker compose stop` で停止、`docker compose start` で再開できます。`docker compose down --volumes` は保存用ボリュームを削除するため、通常の停止には使わないでください。

## ローカルLLMで複数ボットを動かす仕組み

ボットごとに役割、指示、作業コンテキスト、記憶を分け、同じ会話用モデルを利用します。ボットの人数だけモデルのコピーを常駐させる必要はありません。

「設定」→「生成の同時実行」→「同時生成の上限」は初期値1、設定可能な範囲は1～16です。実行中にも変更でき、上限を下げた場合は進行中の生成が終わるのを待ってから新しい要求を通します。ツールや承認の待機中は、別のボットが推論枠を使えます。

ルーム内の並列応答はルームごとに有効にします。無効の場合も、制御するのは一回の推論リクエストであり、一人のボットの作業全体が終わるまで他のボットを止める仕組みではありません。同じボット×ルームのセッションは、並列設定にかかわらず重複実行しません。別のボットへ渡す共有文脈には、生成途中の断片を含めません。画面では推論枠、ルーム内の順番、同じセッション、実行枠の待ちを区別します。

Continuous batching、prefill/decodeの実行順、KVキャッシュ、GPU上の処理は推論サーバーが担当します。Loomはサーバーへ渡す同時リクエスト数を制御します。まず上限2で比較し、応答の待ち時間、全体の処理量、メモリ使用量を確認して増減してください。上限を増やせば一つひとつの応答が速くなる、とは限りません。

画面はReact/TypeScript、バックエンドもTypeScript/Node.jsです。Piをバックエンドに組み込み、モデルとツールの実行ループを担当させています。モデルの読み込みやGPU上での推論は、用意した推論サーバーが担当します。

## 別のモデルで画像を生成する

設定の **画像生成** を有効にし、画像生成サーバーのベースURL、モデルID、必要なら専用APIキーを保存します。会話用モデルの接続先・認証情報とは分離されています。対応するのは **OpenAI互換の `POST /images/generations`** です。ComfyUI固有のワークフローAPIに直接接続するアダプターは含まれません。

会話用LLMが `generate_image` を呼ぶと、生成結果をチャットに画像として保存します。PNG・JPEG・WebPに対応し、表示とダウンロードができます。画像はアプリのデータフォルダー内の `generated-images` に保存されます。会話用LLMへ返すのは保存結果のメタデータで、画像の見た目をLLMが確認したことにはなりません。

画像生成は常に1件ずつ実行します。初期設定では会話モデルと推論枠を共有し、同じGPUへの負荷を調整できます。画像モデルを別のマシンなどで動かす場合は、共有を外して会話モデルとの同時実行を許可できます。ネットワーク権限の「自動判定」では、画像生成のプロンプト・モデル・接続先を確認して承認します。

完了済みの同じ生成要求は再開時に画像を復元し、再生成しません。停止やタイムアウトは、画像サーバー側ですでに始まった計算まで止まる保証ではありません。不明な結果を自動で再試行しないため、ログを確認してから新しい依頼を送ってください。詳しい設定範囲は [MODELS.md](MODELS.md) にまとめています。

## 自動処理と通知

自動処理には、実行条件、担当ボット、出力先の部屋、行う内容を設定します。予約起床、一定間隔の定期実行、URL監視、Webhook、接続したアカウントの新着メールを使えます。

ルーム内でボットに「このページを30分ごとに確認して、重要な変更があれば知らせて」のように頼むこともできます。ボットはそのルームの自動化の一覧確認・作成・変更・停止・再開を行えます。変更前には、実行条件、日時・曜日・タイムゾーンまたは間隔、遅れた場合の扱い、担当ボット、処理内容を承認カードで表示します。自動実行やボット同士の引き継ぎから新しい自動化を作ることはできません。「日本時間で毎朝9時に、このルームの未完了の作業を確認して」のような日時指定も可能です。毎日同じ時刻に起こす場合は、1,440分間隔ではなく予約起床を使います。自動化の停止は、すでに始まったボットの作業を停止する操作とは別です。

バックエンドが動作していれば、ブラウザーを閉じても自動処理を継続できます。PCのスリープやシャットダウン中は実行されません。現在の通知先はアプリ内の受信箱です。Telegram、Discord、Slack、スマートフォンへのプッシュ配信を行う外部ボットゲートウェイは、この版には含まれません。

### 日時を指定する予約起床

**自動化 → 自動化をつくる → 予約起床**で、一度だけ・毎日・曜日指定から選びます。日時、タイムゾーン、担当ボット、出力先ルーム、任せることを設定すると、次回の起床時刻を確認できます。タイムゾーンの初期値はブラウザーに従います。日本時間なら **Asia/Tokyo** を選んでください。

時刻を過ぎていた場合は、**再開できるときに1回実行する**または**過ぎた分をスキップする**を選べます。通常のチェックは5秒おきです。スキップは予定時刻を1分以上過ぎた場合に適用し、起動中のわずかなチェックの遅れは許容します。複数回分を取り逃しても、大量のタスクをまとめて投入しません。

一度だけの予約は、ボットの作業をキューへ登録した時点で「起床済み」になります。実際の作業の進捗や承認待ちはルームで確認してください。**今すぐ実行すると、その一回分の予約を消費します。** 再度予約するには編集して新しい未来日時を指定します。タイトルや指示だけの変更では、待機中の予約時刻をずらしません。

夏時間のある地域でも、繰り返しは指定した現地時刻を維持します。時計が進んで存在しない時刻になった場合、一度だけの予約は入力エラーにし、繰り返しの該当回はスキップします。時計が戻って同じ時刻が二回来た場合は、最初の一回だけを対象にします。PCの電源投入やスリープ解除は行いません。

### Gmailの受信設定

1. **メール・サービス → メールを接続** でメールアドレスを入力し、**Gmailの接続設定を使う** を押します。
2. Googleアカウントの[2段階認証](https://myaccount.google.com/signinoptions/two-step-verification)を有効にし、[アプリパスワード](https://myaccount.google.com/apppasswords)をAgent Loom用に発行します。
3. IMAPとSMTPのパスワード欄にアプリパスワードを入力します。受信だけなら **SMTPでの送信を設定** をオフにします。受信は `imap.gmail.com:993`、送信は `smtp.gmail.com:465`、どちらもTLSが設定されます。
4. 利用するボットと送信権限を選び、**接続をテスト** で確認して保存します。
5. **自動化 → 新規作成 → 新着メール** でその接続を選び、間隔・ルーム・担当ボット・通知してほしい条件を設定します。自動チェックにはネットワーク権限の **許可** または **自動判定** が必要です。

接続確認は設定を保存せず、メールを送信せず、自動処理を開始しません。パスワードはチャットではなく設定欄に入力してください。保存済みパスワードは同じ接続先・アカウントでのみ保持します。ボットが作った未接続の従来IMAP設定は、無効な下書きとして残ります。メールアカウントを接続してルールに選ぶか、従来設定の **接続を設定** から続けられます。

通常のGoogleアカウントのパスワードは使えません。組織のポリシーや高度な保護機能などにより、アプリパスワードを発行できないアカウントがあります。[Googleの公式案内](https://support.google.com/accounts/answer/185833?hl=ja)を参照してください。個人のGmailでは[IMAPは常に有効](https://support.google.com/mail/answer/7126229?hl=ja)になっており、Gmail側で「IMAPを有効にする」を探す必要はありません。「Googleでログイン」するOAuth方式は、この版には未実装です。

その他のIMAPサーバーも「メール・サービス」から接続できます。従来のGmail/IMAPプリセットは自動化エディターの **従来のIMAP接続を使う** に残っています。Webhookには自動処理ごとの専用トークンを使います。詳しい設定は [INSTALL.md](INSTALL.md) と [API.md](API.md) を参照してください。

URL・メールの自動ポーリングには、ネットワーク権限を **許可** または **自動判定** にする必要があります。チェックは件数を区切り、進捗を保存して続けます。接続済みアカウントのルールは、ルール作成後から初回確認までに届いたメールも対象にします。従来のインラインIMAP設定は、初回確認時のUIDを基準にする動作を維持します。ポーリング自体では送信や既読化を行いません。接続したアカウントでは、ボットが必要なメール本文を別途取得し、権限に従って返信の下書きを用意できます。設定・受信バッファ・復旧の詳しい説明は [MAIL.md](MAIL.md)、自動化全般は [INSTALL.md](INSTALL.md) を参照してください。

## 保存場所と更新

通常起動時の保存先は `.loom` です。会話、部屋、作業、記憶、スキル、設定などをSQLiteに保存し、画像添付は `generated-images` に保存します。保存する接続用シークレットは、同じデータディレクトリ内の `secret.key` を使って暗号化します。会話や生成画像などはLoom自身では暗号化しません。

バックアップはアプリを停止したうえで、データディレクトリを丸ごとコピーしてください。データベースだけでは、暗号化した認証情報を復元できません。データと鍵の両方を保持し、バックアップも保護してください。既定またはルームごとの作業フォルダーを別の場所に指定している場合、そのフォルダーも別途バックアップします。

更新時は停止とバックアップの後に実行します。

```sh
git pull --ff-only
npm ci
npm run build
npm start
```

Dockerでは `git pull --ff-only` の後に `docker compose up --build -d` で再ビルドします。

## 開発・検証

```sh
npm ci
npm run dev
```

開発画面は [http://localhost:5173](http://localhost:5173)、開発用APIはポート3211です。通常起動時は画面とAPIをポート3210でまとめて提供します。

```sh
npm run check
```

型検査、テスト、本番ビルド、本番サーバーのHTTP起動確認を実行します。CIにはLinux・Windows・macOSのNode 24と、コンテナのビルド・ヘルスチェックを設定しています。自動テストは再現可能な模擬応答を使用し、モデルのダウンロードや有料API呼び出しを必要としません。利用する実モデルの互換性と性能は、そのモデル・量子化・推論サーバーの組み合わせで確認する必要があります。実施済みの検証と未確認の範囲は [VALIDATION.md](VALIDATION.md) に記録しています。

## 現在の範囲

一人の信頼できる所有者が使う構成を想定しています。複数ユーザーの権限分離、OSレベルのサンドボックス、一般的なMCPクライアント、プラグイン市場、プロバイダーのサブスクリプション/OAuth連携、完全なIDE、モデルの追加学習は未実装です。

操作の承認は内容を確認するための機構です。許可したシェルコマンドには、アプリのOSユーザーと同じ権限があります。公開サーバーでの運用や個人フォルダーのマウントを行う場合は [SECURITY.md](../SECURITY.md) を確認してください。再起動で中断した作業は履歴を確認して明示的に再開しますが、任意の外部操作について「必ず一度だけ実行する」保証はありません。
